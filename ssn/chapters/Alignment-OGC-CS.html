OGC API – Connected Systems Alignment

OGC API – Connected Systems (CSAPI) is a multipart OGC Web API standard for accessing and managing connected systems and their associated resources. Part 1 [[CSAPI-1]] defines feature resources and property definitions; Part 2 [[CSAPI-2]] defines dynamic-data resources, including datastreams, observations, control streams, and commands. CSAPI uses SOSA/SSN concepts as a basis for its resource model and expresses corresponding information through resource representations, attributes, and associations.

The following tables summarize selected conceptual correspondences between CSAPI 1.0 and the vocabulary defined in this edition of SSN. This informative alignment describes CSAPI as specified in the cited OGC standards; it does not modify CSAPI resource definitions, API behavior, encodings, or conformance requirements. The correspondences are not OWL equivalence axioms and do not define an RDF encoding or a complete transformation between CSAPI and SOSA/SSN.

Command sosa:Actuation Conceptual correspondence: CSAPI describes Command as a generalization of Actuation. See the lifecycle note below. Part 2, 10.7

CSAPI System resources represent instances of sosa:System, including more specific types such as sosa:Sensor, sosa:Actuator, and sosa:Sampler. Part 1, 9.1 also describes the case in which an individual is both a sosa:System and a sosa:Platform; it does not make every Platform a System. sosa:Asset is a broader superclass in this edition of SSN.

The definition of sosa:ActuationCollection is non-normative in this edition of SSN. The correspondence above does not change the requirements specified for ControlStream resources in CSAPI Part 2. A Command can be received, scheduled, executed, completed, or rejected; the correspondence with sosa:Actuation does not by itself establish that execution occurred.

The next table identifies the source resource for each attribute or association. Association names may also be used in CSAPI link relations, such as ogc-rel:subsystems; their interpretation depends on the source resource and the association definition. Query parameters select resources and are not themselves RDF predicates.

Membership is read from the DataStream or ControlStream to its Observation or Command members. Where an association is exposed through a link to a list endpoint, the correspondence concerns the associated entities, not the response wrapper or page. These rows do not define a general conversion of links or query results into RDF statements.

The parentSystem correspondence applies to a System that is a subsystem. A SamplingFeature’s parentSystem instead identifies the System that created or uses it. Likewise, the samplingFeatures correspondence above is scoped to DataStream and ControlStream: a System or Deployment can expose associated sampling features without asserting the same direct SOSA/SSN property. No single-property mapping is asserted here for those other contexts.

CSAPI Part 1 uses sosa:hasDeployment for the System deployments association. The table uses sosa:systemDeployment, which denotes the System-to-Deployment relationship in this edition of SSN; it does not assert that the two properties are equivalent.

The sampledFeature correspondence applies only when the target is the ultimate feature of interest, as described in CSAPI Part 1, Table 18. In that case, sosa:isSampleOfUltimateFOI is the name used in this edition for the property previously called sosa:hasSampledFeature. This is not an unconditional mapping of sampled-feature relationships in a sampling chain: an intermediate sample, also discussed in Part 1, 14.2, is not identified here as the ultimate feature of interest.
